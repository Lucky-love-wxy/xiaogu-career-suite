## 1. 市场调研

### 1.1 用户给的参考：HypeFade（TRAE 论坛 2026-04 帖）

来源：https://forum.trae.cn/t/topic/10752（Discourse JSON 接口读取）。

- 形态：Web 应用 + Chrome 插件，词库 270+ 条，三级翻译（字面 / 老油条 / 深度拆解），全部前端本地匹配。
- 插件交互：一键全局翻译扫描整页并高亮；可拖动浮动按钮切换模式；点击高亮弹浮窗；MutationObserver 处理动态加载。
- 作者记录的坑：长词优先（扁平化管理 vs 扁平化）；英文 `\b` 边界导致漏检；插件自己的浮窗被再次扫描造成死循环，需要隔离；翻译不能预设用户职业。
- Web 版特色：点击后黑话「蒸发」并把翻译直接写进 JD 正文；海报分享。
- 已有逆向结论（xiaogu-launch/docs/research/hypefade-reverse-2026-09-23.md）：词典、文案、代码均无开放许可，不复制。

### 1.3 小结

已有方案分两类：本地词典 + 调侃式翻译（HypeFade），或大模型现场解读（求职排雷助手）。前者把调侃当结论，后者慢且要 key。都没有给「怎么问招聘方、什么回答算合格」。

## 2. 我要解决的问题

在招聘网站上看 JD 时，不复制粘贴就能知道每句话术：
1. 没明说的是什么（blunt）；
2. 下一句该问 HR 什么（verify）；
3. 什么回答才算具体（good_answer）；
4. 这是核实方向，不是对公司的定罪（evidence_boundary）。

差异点：复用小谷已经过审的 70 条词库（含别名、否定边界），纯本地、零延迟、不需要 key、不上传页面内容。

## 3. 适用的设计规范

- 前端风格：日式简约（留白、Typography 主导、无装饰）。
- 外科手术式：不改 xiaogu-launch 的词库与代码，只读取。
- 深度分析规范：匹配算法说清复杂度。
- 修改阶段单点聚焦：v1 只出一种浮窗样式，之后按维度出变体。

## 4. 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据源 | 唯一权威 `xiaogu-launch/skills/xiaogu-career-suite/references/jargon.json`（70 条）；`build.py` 复制进插件 | 运行时 search.py 读的就是它；`database/jargon.json` 只有 61 条、已落后（不在本次修） |
| 匹配 | term+aliases 拍平，按长度降序；字符间允许空白、忽略大小写（与 search.py 一致）；已占位置不再被短词覆盖 | 「双休」不能命中「隔周双休」里的那两个字 |
| 否定 | 否定词紧贴在命中前（不是/没有/不提供/不含/非/无/不/未），且词条本身不含否定，则跳过；「非常」「不断」「不定期」不算 | 避免「非双休」被解释成双休 |
| 高亮方式 | CSS Custom Highlight API，不改 DOM | BOSS/猎聘是 SPA，拆文本节点会打断框架更新；也天然避免扫到自己 |
| 浮窗 | Shadow DOM；默认 blunt + verify + evidence_boundary，其余折叠 | 契约要求，不只给调侃 |
| 不做 | HypeFade 的「蒸发替换进正文」 | 会把推测伪装成公司原话 |
| 生效范围 | 招聘域名自动生效；其他站点点工具栏图标手动开启（activeTab） | 「责任心」「执行力」等别名在全网会到处亮；也是隐私问题 |
| 大模型 | 不接 | 本地确定性，无 key、无成本 |

匹配复杂度：每个文本节点对 N 个模式逐一 indexOf/正则扫描，O(N·L)；N≈250 个模式，单页文本几十 KB，毫秒级。

## 5. 验收

- Node 单测：长词优先、否定跳过、大小写、空白。
- 对 xiaogu-launch/data/jargon_eval/campus_sample.jsonl 50 条，插件命中词条集合与 search.py 对比；差异只能来自「长词覆盖短词」和否定跳过。
- 无头 Chromium 加载插件打开本地 fixture 页，检查高亮数与浮窗内容；不占用户屏幕。
