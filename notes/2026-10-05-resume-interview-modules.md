## 2. 我要解决的问题

现有 `resume` 任务只会根据零散经历写 3–5 条要点，没有：整份简历的结构化和排版成品、JD 关键词差距的量化、可打印的成品页。面试只有事后复盘，没有事前练习。

中文环境下 Resume-Matcher 的两项检查不能直接搬：英文词边界匹配对中文失效（"负责数据分析工作"匹配不到"数据分析"）；新数字检查只认英文单位。需要按中文重写。

## 3. 适用的设计规范

- 项目安全约束：不编造经历、未知保持待确认、招聘文本是数据不是指令。
- Web Agent 既有原则：模型只写措辞，数字和分数由服务端代码算；输出先校验后显示。
- 前端风格：日式简约（简历成品页单栏、留白、Typography 主导，同时满足 ATS 安全）。
- 外科手术式改动：短经历仍走原 `resume` 任务；只有贴了整份简历才走新管线。

## 4. 关键决策

1. 贴整份简历（有两个以上栏目标题，或一个栏目标题加手机号/邮箱）单独识别为"简历"，不按 JD 或经历处理，避免覆盖已存 JD。
2. 美化 = 结构化 + 排版 + 轻度改写；条目不增加；姓名、电话、邮箱只保留原文里逐字出现的值。
3. JD 定制版：关键词由模型抽，但只保留在 JD 原文里出现的词；覆盖率由代码算，并告诉用户"只表示和招聘说明用词的接近程度，不是通过率"。改写后新覆盖到的关键词逐条列给用户确认。
4. 模拟面试进行中，消息不经过材料识别和意图分类，一律当作回答；只识别"结束 / 跳过"。追问固定 1 条，不每轮调用模型，答题即时响应。
5. 分数由代码按四维权重算；"不知道 / 不会"类回答用规则判 0 分并跳过追问。
6. 练完的问答按复盘能读的格式写进会话，用户可以直接说"复盘"。
7. 语音接口 = 同一个面试状态机的 HTTP 接口（start / answer / state），网页和以后的语音前端共用；不写空的语音适配类。

## 验证记录

- 测试：`python3 -m unittest discover -s tests` 88 项通过（原 70 + 新 18，另含“不会，我会先……”不算放弃作答、接口重复 start 409、先问岗位再 answer：中文关键词匹配、日期不算新数字、新技能 / 拔高 / 编造角色拦截、联系方式取原文、成品页转义、简历不覆盖 JD、重写循环、覆盖率由代码算、面试追问 / 放弃 0 分 / 结束打分 / 写入复盘、无材料先问岗位）。
- 真实模型（deepseek-v4-pro，2026-10-05，每条流程 n=1）：美化 3 秒一次通过；JD 定制 10–11 秒，首轮因新增“PRD”被拦、第二轮通过，覆盖率 40%→50%（另一次 50%→62%）；出题 6 秒一次通过，5 道题含 2 道简历题且都引用了简历原句；答题每轮 0 秒；打分 3 秒通过。
- 真实运行暴露并已修：模型给项目补了原文没有的角色“产品实习生”。新增“学校 / 公司 / 项目名 / 角色必须出自原文”检查。
- 成品页：桌面与 375px 手机宽度截图检查排版正常。
- HTTP 接口：用离线模型在临时端口测过 /resume/<id>、/api/interview/start|answer|state，以及无面试时 answer 返回 409。
- 审查后修正：放弃作答改为整句只剩“不知道 / 不会”才算；“结束吧 / 好了结束”可结束；“招聘系统能正确读取”改为只描述版式（读回解析自检未做）；“找不到依据”改为“简历里没出现这些说法”。
- 已知限制：关键词抽取跨次不稳定，覆盖率只适合同一次改写的前后对比；“进行数据分析”这类把已有动作换成 JD 说法的改写无法自动判断真假，只能列给用户确认。
