## 1. 市场调研结果（已知方法，未做实时检索）

这次不另写 Codex brief。原因是这些方法很成熟，本次只需要取其中的机制，不用重新比较。

| 方法 | 解决什么 | 怎么解决 | 取用 |
|---|---|---|---|
| ADR（Michael Nygard, Architecture Decision Records） | 事后不知道「当时为什么这么定」 | 每个决策一页：背景 / 决策 / 后果，只追加，被推翻时标 superseded | 取「只追加 + 被推翻要标注」 |
| Google SRE 无责复盘（postmortem） | 出事后只追责，不找机制原因 | 时间线 + 根因 + 行动项，对事不对人 | 取「时间线必须带来源」 |
| Annie Duke 决策日志 / resulting 偏差 | 用结果好坏反推决策好坏 | 决策当下写下预期和置信度，事后对照 | 取「决策时写预期」，**本项目缺的就是这条** |
| Gary Klein pre-mortem | 事前看不到失败路径 | 假设已经失败，倒推原因 | 只用于大转向前，不常规化 |
| Amazon COE（Correction of Error） | 同类错误反复出现 | 五问 + 行动项追踪到关闭 | 取「行动项要有关闭状态」 |

## 4. 方案

### 4.1 回溯：时间线 v0（本次交付）

文件：`docs/retro/timeline.md`。每行写「日期 | 事件 | 类型 | 来源」。类型有五种：起点 / 决策 / 转向 / 踩坑 / 验收。
来源按可信度排：git > notes > changelog > memory 更正 > Codex 会话首条指令。没有来源的事件不写入。

### 4.2 往后：三个最小增量（不另建系统）

1. 启动文档加「下注」三行，写在方案节末尾：
   - 当时的决策
   - 预期结果：可验证的说法，最好带数字
   - 怎么验证、哪天验证

   复盘时用实际结果对照预期，四格判断：好决策好结果 / 好决策坏结果 / 坏决策好结果 / 坏决策坏结果。
2. 时间线只追加：每次转向、验收、踩坑后追加一行，并带来源。不允许改旧行；结论被推翻时，新开一行写「推翻 #N」。
3. 里程碑用 git tag 做检查点。git 补齐前，时间线里的阶段边界只能靠 notes 推断，精度到天。

### 4.3 正式复盘怎么做（项目到一定程度时）

- 触发：上线内测、或明确转向、或连续两周无实质推进。
- 输入：timeline.md + 各 notes 的「下注」节。
- 输出：`docs/retro/retro-YYYY-MM-DD.md`，含三段：
  - 做对了：预期兑现的下注
  - 做错了：预期落空，并区分是信息不足、判断错还是执行没跟上
  - 重复模式：同类错误出现两次及以上的
- 每条结论都要引用时间线行号。
